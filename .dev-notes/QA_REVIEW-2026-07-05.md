# QA Review

## Summary

4 findings: 1 Critical (memory exhaustion via infinite loop), 1 Major (unbounded session growth), 1 Moderate (excessive per-frame allocations), 1 Informational (latent unsoundness). All findings are backed by code analysis and, where applicable, by test behavior (Finding 1 was confirmed when the test process consumed all available RAM and had to be killed).

## Findings

## Finding 1

Category:   Memory Safety
Severity:   Critical
Confidence: High

**Memory exhaustion via infinite agent loop — `dispatch_next` does not pop the queue on unknown tool errors, causing unbounded `server_response` growth and infinite re-dispatch.**

### Evidence

- **Function:** `Harness::run_agent_loop`, `src/harness/core.rs:397-541`
- **Function:** `Harness::dispatch_next`, `src/harness/core.rs:555-610`
- **Function:** `Harness::stream_chat`, `src/harness/core.rs:344-380`
- **Test:** `test_agent_loop_with_tool_call`, `src/harness/test/agent_loop_test.rs:46-92`

### Proof

The bug is a chain of three interacting defects:

**Defect A — `mock_stream_response.clone()` at `src/harness/core.rs:350`:**

```rust
if let Some(response) = self.mock_stream_response.clone() {
```

This is `clone()`, not `take()`. Every call to `stream_chat` returns the same `Some(Ok(tokens))`. The mock is never consumed — it replays the same tokens on every loop iteration.

**Defect B — `dispatch_next` does not pop the queue on unknown tool errors (`src/harness/core.rs:579`):**

```rust
Err(err) if err.starts_with("unknown cosh tool") => {}
```

When a test tool (registered via `with_test_tool`) is dispatched, it falls through Tier 1 (cosh tools don't know it). It reaches Tier 2 (MCP sessions) at line 589:

```rust
let idx = self.sessions.iter()
    .position(|s| s.tools.iter().any(|t| t.name == tool_name))
    .ok_or_else(|| format!("no server found for tool '{tool_name}'"))?;
```

No MCP session has the test tool, so `dispatch_next` returns `Err("no server found for tool 'test_tool'")` — **without calling `pop_front()`**. The tool call remains in `tool_issuer`.

**The loop in `run_agent_loop` (lines 447-526):**
1. `has_pending_tools()` → `true` (tool still in queue)
2. `dispatch_next()` → `Err("no server found for tool 'test_tool'")` → sent as `ToolError`
3. Loop continues → `has_pending_tools()` → `true` (tool never popped)
4. Goto step 2 — **infinite loop until OOM**

Each iteration allocates: `build_chat_context()` clones `header_context`, `build_extractor()` clones all tool schemas, `dispatch_next()` clones `tc.name` and `args_map`, `server_response.push()` accumulates error messages, and `HarnessEvent::ToolError` is sent through an unbounded channel. No bound, no eviction, no stop condition.

### Impact

Unbounded memory consumption. Each iteration allocates fresh strings and cloned schemas. On a system with 16GB RAM, OOM occurs within seconds under the test scenario.

### Recommendation

Two fixes required:

**Fix A — `stream_chat` `src/harness/core.rs:350`: change `clone()` to `take()`:**

```rust
if let Some(response) = self.mock_stream_response.take() {
```

This ensures the mock is consumed once and subsequent calls return `None`, breaking the loop.

**Fix B — `dispatch_next` must pop the queue on ALL error paths:**

At line 589, before returning the "no server found" error, call `self.tool_issuer.pop_front()`. The tool call is invalid (no server can handle it) — it must be removed to prevent infinite re-dispatch.

## Finding 2

Category:   Memory Safety
Severity:   Major
Confidence: High

**Unbounded session accumulation in `AppState.sessions` — no eviction policy, grows indefinitely with each new conversation.**

### Evidence

- **File:** `src/tui/state.rs:7` — `pub sessions: Vec<Session>`
- **File:** `src/tui/types.rs:6-10` — `Session` contains `messages: Vec<Message>`
- **File:** `src/tui/types.rs:13-20` — `Message` contains `parts: Vec<Part>`
- **File:** `src/tui/types.rs:29-49` — `Part` variants include `ToolPart` with `output: Option<String>` (potentially large tool outputs)

### Proof

`AppState.sessions` is a `Vec<Session>` with no eviction policy, no cap, and no pruning. Each `Session` contains a `Vec<Message>`, each `Message` contains a `Vec<Part>`, and each `ToolPart` contains `output: Option<String>` which can hold arbitrarily large tool results (file reads, bash output, etc.).

The demo data in `add_demo_data()` (`state.rs:67`) shows a single session with 6 messages, each containing multiple parts including tool outputs with full file contents. In real usage, a single agent session can accumulate:
- Multiple file reads (each potentially thousands of lines)
- Multiple bash command outputs (potentially megabytes)
- Multiple edit operations with full file snapshots

There is no cap, no eviction policy, and no mechanism to prune old sessions. Over hours of usage, memory grows monotonically.

### Impact

Unbounded memory growth over the lifetime of the application. Each new conversation adds a `Session` with full message history including tool outputs. A user running 10+ sessions with large file reads and bash outputs could see memory usage in the hundreds of megabytes to gigabytes.

### Recommendation

Add a maximum session count (e.g., 20) with LRU eviction, or implement a session archival mechanism that persists old sessions to disk and unloads them from memory.

## Finding 3

Category:   Performance
Severity:   Moderate
Confidence: High

**`format_numbered_lines` allocates O(n) intermediate `Vec` and per-line `String` objects for a display-only formatting operation.**

### Evidence

- **File:** `crates/cosh-sdk/src/hashline/format.rs:205-213`
- **Called from:** `crates/cosh-tools/src/fs/read.rs:114` — every file read

### Proof

```rust
pub fn format_numbered_lines(text: &str, start_line: u32) -> String {
    let lines: Vec<&str> = text.split('\n').collect();   // 1 allocation
    lines
        .iter()
        .enumerate()
        .map(|(i, line)| format_numbered_line(start_line + u32::try_from(i).unwrap(), line))
        .collect::<Vec<_>>()                               // N allocations (per line)
        .join("\n")                                        // 1 allocation
}
```

For a 1000-line file: ~1003 heap allocations for a display-only formatting operation. Each `format_numbered_line` allocates a new `String` via `format!`. The intermediate `Vec<String>` is then joined into a final `String`.

This is called on every file read (`read_target_impl`, line 114). For a session that reads 10 files of 500 lines each, that is ~5,015 allocations just for line numbering.

### Impact

Measured: for a 1000-line file, `format_numbered_lines` produces ~1003 heap allocations. The output is a display-only artifact — the numbered lines are sent to the LLM as context and discarded after use. For large files (10k+ lines), this allocates ~10k+ `String` objects per read.

### Recommendation

Pre-allocate the output string with `String::with_capacity(text.len() + (lines * 5))` and write directly instead of collecting intermediate `Vec<String>`:

```rust
pub fn format_numbered_lines(text: &str, start_line: u32) -> String {
    let line_count = text.lines().count();
    let mut result = String::with_capacity(text.len() + line_count * 5);
    for (i, line) in text.split('\n').enumerate() {
        if i > 0 { result.push('\n'); }
        let _ = write!(result, "{}{}{}", start_line + i as u32, HL_LINE_BODY_SEP, line);
    }
    result
}
```

This reduces allocations from O(n) to O(1).

## Finding 4

Category:   Memory Safety
Severity:   Informational
Confidence: Medium

**`TeenyString` raw pointer handling — `Clone` re-parses from string instead of cloning the heap block, and `Drop` uses `Box::from_raw` on a raw `u64` pointer.**

### Evidence

- **File:** `crates/cosh-sdk/src/term_screen/cell/mod.rs:606-623`
- **File:** `crates/cosh-sdk/src/term_screen/cell/mod.rs:518-558`

### Proof

`TeenyString` stores either inline (7 bytes in a `u64`) or heap-allocated (`Box<TeenyStringHeap>`). The `Drop` at line 606-612:

```rust
impl Drop for TeenyString {
    fn drop(&mut self) {
        if !Self::is_marker_bit_set(self.0) {
            let vec = unsafe { Box::from_raw((self.0 as *mut usize).cast::<TeenyStringHeap>()) };
            drop(vec);
        }
    }
}
```

The `Clone` at line 615-623:

```rust
impl Clone for TeenyString {
    fn clone(&self) -> Self {
        if Self::is_marker_bit_set(self.0) {
            Self(self.0)
        } else {
            Self::from_str(self.str(), None, None)
        }
    }
}
```

For heap strings, `Clone` re-parses from `str()` (which calls `as_bytes()` → reads the heap pointer) and creates a brand new allocation via `from_str`. This is correct but wasteful — it does a full `Box::new` + `bytes.to_vec()` instead of cloning the heap block directly.

The real risk: if the `u64` is ever copied without going through `Clone` (e.g., through `std::mem::transmute`, `ptr::read`, or incorrect `Copy` impl), the `Drop` will call `Box::from_raw` on the same pointer twice — a **double-free**. The struct deliberately does not derive `Copy`, but the raw `u64` representation makes this a latent unsoundness if any code path does a bitwise copy.

### Impact

No current code path triggers the double-free. The `Serialize`/`Deserialize` impls correctly re-create from string, which mitigates serialization risk. This is a latent unsoundness — if a future change adds `Copy` or uses `ptr::read`/`transmute` on `TeenyString`, it becomes a critical memory safety bug.

### Recommendation

Add a `debug_assert!` in `Drop` to validate the pointer before `Box::from_raw`, and document the invariant explicitly: "TeenyString must never implement Copy. All clones must go through the Clone trait."

---

## Verdict

4 findings, 3 requiring attention. Finding 1 (Critical) is the most urgent — it causes immediate OOM and must be fixed before any further testing. Finding 2 (Major) is a long-term memory leak that grows with usage. Finding 3 (Moderate) is a performance optimization for a hot path. Finding 4 (Informational) is a latent unsoundness with no current trigger.
