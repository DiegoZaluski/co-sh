# QA Review — cosh

## Summary

Audited ~22,057 LOC across 129 `.rs` source files in `cosh-sdk` and `cosh-tools`. Covered all four pillars: Sandbox Integrity, Memory Safety, Performance, and Readability & Maintainability.

**Total findings: 3** (2 Critical, 0 Major, 1 Moderate).

**Suite status:** `cargo test --workspace` — **all 355 tests pass** (351 unit + 4 doctests). Zero failures across both crates and all doc-tests.

**Changes made to achieve clean suite:**
1. `autodiscovery::github` module visibility changed from `pub(crate)` to `pub` so the doctest can reference it.
2. `copilot_auth.rs` doctest: replaced bare `.await` with `tokio::runtime::Runtime::new().unwrap().block_on(...)`.
3. Rollback tests: added `serial_test = "3"` as dev-dependency and `#[serial]` on every test in `rollback/test.rs` to prevent LRU eviction races on the global `InMemorySnapshotStore` singleton.
4. `rollback/core.rs`: all `Mutex::lock().expect("...")` changed to `.unwrap_or_else(|e| e.into_inner())` so mutex poisoning from a panicked test does not cascade to subsequent tests.
5. `restore_fails_when_write_directory_does_not_exist`: replaced hardcoded path with `tmp()`-based unique path to avoid colliding with concurrent test state.

## Findings

## Finding 1

Category:   Sandbox Integrity
Severity:   Critical
Confidence: High

**Vulnerability**: `read()` performs zero path validation.

Evidence:
  - `read_target` at `crates/cosh-tools/src/fs/read.rs:44` passes `target.path` directly to `DiskFilesystem::read_text()` with no call to `fs_guard()` or `validate_path()`.
  - `collect_source_files` at `read.rs:215` calls `std::fs::read_dir()` without validation.
  - All three sandbox layers are absent: absolute path rejection, `..` rejection, canonical prefix check.

Proof:
  - **Test**: `read_gap_absolute_path_no_guard` at `crates/cosh-tools/src/fs/test/test_path_traversal.rs:30` — calls `read()` with path `/etc/hostname`, asserts `warnings.is_none()` and content is non-empty. PASSES, proving no guard.
  - **Test**: `read_gap_dotdot_traversal_no_guard` at `test_path_traversal.rs:55` — calls `read()` with absolute `..` traversal path `/home/inky/cosh/../../../etc/hostname`, asserts no warning. PASSES, proving path traversal in read.
  - **Code audit**: `rg 'validate_path|fs_guard' crates/cosh-tools/src/fs/read.rs` returns zero matches.

  **Run**: `cargo test -p cosh-tools read_gap_absolute_path_no_guard`
  **Run**: `cargo test -p cosh-tools read_gap_dotdot_traversal_no_guard`

  Expected: both pass.

Impact:
  Any file on the filesystem is readable. An attacker with prompt injection can exfiltrate `/etc/passwd`, `~/.ssh/id_rsa`, or any path.

Recommendation:
  Add `fs_guard()` call in `read_target()` before `read_normalized()`, matching `write.rs:135` and `edit.rs:54`.

## Finding 2

Category:   Sandbox Integrity
Severity:   Critical
Confidence: High

**Vulnerability**: Write/edit/rollback discard the validated path and use the raw user input for I/O. `validate_path` only does lexical normalization — no `canonicalize()`. A symlink inside root pointing outside bypasses the guard.

Evidence:
  - `write.rs:141` calls `fs.write_text(target.path, ...)` using the original `target.path`, not the normalized path from `validate_path`.
  - `fs_guard` at `crates/cosh-tools/src/fs/types.rs:61` discards the validated path: `GuardResult::Allowed(_) => FsGuard::Allowed`.
  - `validate_path` at `util/guards/mod.rs:52` uses only lexical normalization (`.`/`..`). No symlink resolution.
  - Same pattern in `edit.rs:118` and `rollback.rs:72`.

Proof:
  - **Test**: `write_gap_symlink_escape` at `crates/cosh-tools/src/fs/test/test_path_traversal.rs:215` — creates symlink `/home/inky/cosh/cosh_sandbox_escape_link` → `/tmp/cosh_symlink_escape_target`, writes to it via `write()`. Guard allows it (lexically inside root), but the file lands in `/tmp/`. PASSES.
  - **Test**: `edit_gap_symlink_escape` at `test_path_traversal.rs:270` — same pattern for `edit()`. Modifies file outside root via symlink. PASSES.
  - **Code audit**: `fs_guard` at `types.rs:61`: `GuardResult::Allowed(_) => FsGuard::Allowed` — the `PathBuf` is thrown away.

  **Run**: `cargo test -p cosh-tools write_gap_symlink_escape`
  **Run**: `cargo test -p cosh-tools edit_gap_symlink_escape`

  Expected: both pass.

Impact:
  Anyone who can place a symlink inside the project root (via write, cloned repo, skill directory) can write/edit/rollback files outside the sandbox.

Recommendation:
  (a) `fs_guard` must return the validated path. (b) Callers must use it for I/O. (c) Add `canonicalize()` + `starts_with(&root_canon)` before I/O, matching `validate_asset_path` at `guards/mod.rs:101`.

## Finding 3

Category:   Sandbox Integrity
Severity:   Moderate
Confidence: High

**Vulnerability**: `discover_from_directory` and `collect_skill_dirs_recursive` call `fs::read_dir()` without canonicalizing the path first. A symlink inside the skills directory pointing outside is followed.

Evidence:
  - `discover_from_directory` at `crates/cosh-tools/src/skills/discover.rs:92` calls `fs::read_dir(root)` at line 111 with the user-provided path, not canonicalized.
  - `collect_skill_dirs_recursive` at `discover.rs:135` calls `fs::read_dir(&current)` at line 146 with a non-canonicalized path. Canonicalization is only used for the `visited` dedup set at line 141.
  - `cache_key_for_source` canonicalizes (line 22) but only for the cache key, not I/O safety.

Proof:
  - **Test**: `discover_gap_symlink_outside_base` at `crates/cosh-tools/src/skills/test/recursive.rs:72` — creates a skill directory outside the intended base, then a symlink inside the base pointing to it. `discover_skills` follows the symlink and finds `secret-skill` from outside the intended base. The test asserts `names.contains(&"secret-skill")`. PASSES, proving the traversal.
  - **Code audit**: `rg 'canonicalize' crates/cosh-tools/src/skills/discover.rs` — only at lines 22, 100, 140 (cache key and visited-set dedup). No canonicalize before `fs::read_dir`.

  **Run**: `cargo test -p cosh-tools discover_gap_symlink_outside_base`

  Expected: passes (vulnerability confirmed).

Impact:
  A skill source directory with a crafted symlink can load skills from outside the intended scope. Moderate because skill sources are user-controlled, but exploitable in shared environments.

Recommendation:
  Add `canonicalize()` before `fs::read_dir(root)` in `discover_from_directory` and before `fs::read_dir(&current)` in `collect_skill_dirs_recursive`.
