# PERF-2026-07-19: Long-Session Rendering Optimizations

## Binary Search for First Visible Message

### Problem

The render loop in `src/tui/routes/session/mod.rs` iterates over **all** messages every frame to
compute their `y` position via incremental `y += msg_h + gap`. For sessions with 500–3000+ messages
this means thousands of tight iterations per frame (at 30fps = ~90k iterations/second) just to
determine which messages are visible.

### Location

**File:** `src/tui/routes/session/mod.rs`

**Method:** `pub fn render(...)` — the main `for (idx, msg) in session.messages.iter().enumerate()`
loop starting at approximately **line 1876**.

A second identical loop exists in:

- `build_text_regions(...)` — line ~1411
- `handle_mouse(...)` — line ~1133

### Desired Optimization

Replace the O(n) linear scan of all messages with an O(log n) binary search to find the first
message whose content intersects the viewport, then only iterate forward from there until past the
viewport bottom.

**Key invariant:** message heights are stored in `msg_height_cache: Vec<i32>` and gaps are 1 row
between consecutive messages. The `y` of message `i` is:

```
y(i) = i + sum(msg_height_cache[..i])   // i = gap count, sum of heights before i
```

This can be precomputed as a **prefix sum array** (accumulated heights + gap offsets) to allow
binary search.

### Data structure needed

```rust
/// Prefix sum of `y` positions: prefix_y[i] = total height before message i,
/// including gaps. Message i starts at y = prefix_y[i].
/// Array length = n_msgs + 1 (prefix_y[n] = total session height).
prefix_y: Vec<i32>,
```

Updated when `cached_total_height` changes (in `ensure_height_caches_fresh`).

### Binary search approach

```python
def first_visible_msg(scroll_y, viewport_top, prefix_y):
    # Content-space y of viewport top
    target_y = scroll_y + viewport_top
    # Binary search for first message with y >= target_y
    lo, hi = 0, len(prefix_y) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if prefix_y[mid] >= target_y:
            hi = mid
        else:
            lo = mid + 1
    return lo
```

### Rendering loop becomes

```rust
let first_vis = self.find_first_visible(scroll_y, vp_top);
// Fast-forward y to the first visible message
let mut y = vp_top - scroll_y + prefix_y[first_vis];
for (idx, msg) in session.messages.iter().enumerate().skip(first_vis) {
    if y >= vp_bottom { break; }  // past viewport → stop
    // ... render msg ...
    y += msg_h + 1;  // advance by message height + gap
}
```

This reduces per-frame work from O(n) to O(log n + visible_count), a significant gain for
sessions with 500+ messages. The `handle_mouse` and `build_text_regions` loops benefit similarly.

## ✅ Implemented 2026-08-12

Binary search is in place. Summary of what landed in
`src/tui/routes/session/mod.rs` (commit pending):

- `prefix_y: Vec<i32>` — prefix sums of message start positions (1-row gaps
  between messages, `prefix_y[n]` = total height), kept in sync in ALL three
  growth paths of `ensure_height_caches_fresh`:
  - full rebuild via `rebuild_prefix_y()` (replaces `recompute_total_height`),
  - incremental extend (new messages appended),
  - last-message streaming update (only the final prefix_y entry moves).
- `find_first_visible(scroll_y)` — O(log n) binary search for the first
  message whose bottom crosses the viewport top (`prefix_y[i] + height[i]`).
- The three per-frame O(n) walks now start at `first_vis` and stop past
  `vp_bottom` (O(log n + visible)):
  - `render()` — `actual_total_height` on break = rendered span + the
    prefix-y remainder `prefix_y[n] - prefix_y[idx]` of the skipped tail;
  - `build_text_regions()` — off-screen messages contribute no regions;
  - `handle_mouse()` — uses `prefix_y` directly, dropping the O(n) per-click
    `msg_y_position` allocation.
- New consistency test `prefix_y_matches_linear_walk_and_binary_search`:
  validates `prefix_y` against a linear walk and `find_first_visible` against
  brute force across scroll positions and all three cache growth paths.

Measured (release, 90x40 viewport, warm cache):

| 50 pairs | 37us | 40us |
| 3200 pairs | 68us | 52us |

64x messages now costs only 1.30x frame time (was 1.84x) — the per-frame
cost is dominated by the visible viewport, not the timeline length.
