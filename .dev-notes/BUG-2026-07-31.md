# Bug Report: Agent Harness — 7 Confirmed Bugs

**Date:** 2026-07-31

## Scope

Audited components and their interaction with `run_agent_loop`:

- `src/harness/core.rs` — agent loop, message assembly, tool dispatch, fallbacks
- `src/harness/events.rs` — loop-to-TUI event channel
- `src/harness/guardrails.rs` — permission checks
- `src/harness/correction_memory.rs` — tool-error correction feedback
- `src/harness/context_manager/` — layered context compression
- `src/harness/tools.rs` — cosh tool dispatch
- `crates/cosh-sdk/src/extract_action/` — tool-call extraction
- `crates/cosh-sdk/src/connector/` — provider streaming (`openai_compatible`, `claude`)
- `src/tui/app.rs` — loop wiring, history assembly, channels

## Methodology

Each bug was reproduced deterministically by a reproducer test in
`src/harness/test/bug_hunt.rs`. The assertions encode the expected (correct)
behavior and fail under the current implementation, confirming the bug.

Suite results:

- 7 reproducer tests fail (one per bug)
- 56 pre-existing harness tests pass
- 0 compiler warnings

## BUG-01 — User input duplicated in the first request

**Observed behavior:** the first request's messages array contains the user
input twice (`role: "user"`, `content == input`). The reproducer measured 2
occurrences; expected 1.

**Root cause:** the input is inserted through three independent paths that are
merged without deduplication:

1. The TUI (`src/tui/app.rs`) includes the just-sent message in the turns
   passed to `with_history()`.
2. `run_agent_loop` pushes the input into `history`.
3. `build_conversation_messages` appends `current_input` as a user message at
   the end of the array.

Within the harness itself, two copies originate from paths 2 and 3; the TUI
layer (path 1) adds a third copy in the full flow.

**Evidence:** `bug01_user_input_is_duplicated_in_first_request` fails with
`BUG-01: user input must be sent exactly once, but was sent 2 times in the first request`.

## BUG-02 — `total_history_tokens` reset at loop start

**Observed behavior:** with ~60k tokens loaded via `with_history()`, after
`run_agent_loop` runs, `total_history_tokens` is ~1.

**Root cause:** `run_agent_loop` assigns `self.total_history_tokens = input_tokens`
(assignment, not `+=`), wiping the count accumulated by `with_history()`. The
`HISTORY_BUDGET` (50_000) check in `build_conversation_messages` therefore never
fires for loaded turns, and the full raw history is resent on every request.

**Evidence:** `bug02_history_token_counter_wiped_by_loop_start` fails with
`run_agent_loop reset total_history_tokens to 1`.

---

## BUG-03 — Extraction-failure retry has no iteration cap

**Observed behavior:** with 25 queued mock responses of invalid tool JSON, the
loop ran 25 retry iterations; each iteration emitted one "⚠ Tool call failure"
token. `MAX_ITERATIONS` is 20.

**Root cause:** `MAX_ITERATIONS` is only checked inside
`while self.has_pending_tools()`. The extraction-failure retry path
(`!had_tools && extraction_failures > 0`) loops unconditionally; each iteration
costs one LLM call.

**Evidence:** `bug03_extraction_failure_retry_has_no_iteration_cap` fails with
`retry loop must stop at MAX_ITERATIONS (20), but ran 25 iterations`.

---

## BUG-04 — `stop_agent_loop` drops pending tool calls

**Observed behavior:** when a tool call and `stop_agent_loop` are emitted in
the same response, no tool outcome event (result or error) is emitted, and the
tool call remains in `tool_issuer` after the loop exits.

**Root cause:** `handle_harness_tool` sets `self.stop = true` during phase-1
streaming. The `check_stop!()` after phase 1 breaks the loop before phase 2
dispatches the queued tool call.

**Evidence:** `bug04_stop_agent_loop_drops_pending_tool_calls` fails with
`pending tool call was never dispatched — silently dropped by stop_agent_loop`.

---

## BUG-05 — `ask_questions` answer wait not interruptible by `stop_signal`

**Observed behavior:** after the loop emits `QuestionRequest` and `stop_signal`
is set to `true`, the loop does not terminate within 400ms.

**Root cause:** the permission wait uses `tokio::select!` with a `stop_signal`
poll; the `ask_questions` answer wait is a bare `answer_rx.recv().await` with no
stop check. The TUI keeps the answer sender alive for the whole session
(`App::answer_tx`), so `recv()` blocks indefinitely if no answer is sent.

**Evidence:** `bug05_question_answer_wait_ignores_stop_signal` fails after the
400ms timeout elapses.

---

## BUG-06 — Fallback switch loses native tool definitions

**Observed behavior:** after a connector error triggers the fallback switch
(provider "claude"), the active connector reports `has_tools() == false`.

**Root cause:** `init_native_tools()` runs once at loop start. On fallback,
`self.connector` is replaced via `c.with_model(...)` without re-registering
native tool definitions (`set_tools`). The fallback provider receives requests
with no tool definitions.

**Evidence:** `bug06_fallback_switch_loses_native_tools` fails with
`fallback connector has NO native tool definitions`; the provider assertion
(`Some("claude")`) confirms the switch occurred.

---

## BUG-07 — Full conversation sent twice per request

**Observed behavior:** a single conversation turn appears in both the system
context and the messages array of the same request.

**Root cause:** `build_chat_context()` appends the full ContextManager buffer
(via `format_context()`, rendered as "## Compressed Context") to the system
prompt, while `build_conversation_messages()` sends the same turns as messages.

**Evidence:** `bug07_full_conversation_sent_twice_system_and_messages` fails
with `conversation turn sent twice — system_ctx=true, messages=true`.

## Test integrity verification

- **Failure messages verified:** each of the 7 reproducers fails on its
  intended assertion; no unrelated crashes.
- **Mutation check:** with the 7 corresponding minimal fixes applied
  simultaneously, all 63 harness tests pass; after reverting, the suite returns
  to 7 failing / 56 passing, with no leftover mutation code and zero compiler
  warnings. Each reproducer passes when its bug is corrected, confirming the
  tests detect their respective bugs and fail for no collateral reason.
- **Test-design correction:** the BUG-04 assertion originally required
  `ToolResult`. `my_tool` has no dispatch target in `new_test()` (no MCP
  session; `cosh_tools` is `None`), so a correct implementation emits
  `ToolError` ("no server found"), never `ToolResult`. The assertion was
  adjusted to accept `ToolResult | ToolError`; the property verified is that
  the tool call was processed rather than dropped.
