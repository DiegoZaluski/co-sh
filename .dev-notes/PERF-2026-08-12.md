# PERF-2026-08-12: Long-Session Resource Accumulation — Measured Map

**Date:** 2026-08-12

## Method

- New release-only benchmarks probe the two hot paths that accumulate over a
  long session: the TUI session render (`src/tui/routes/session/tests.rs`) and
  the harness context manager (`src/harness/context_manager/test.rs`).
- `heaptrack` profile of a minimal render run
  (`bench_render_heaptrack_minimal`, 6 frames) to attribute allocation sites.
- All measurements below are from a RELEASE build; run the probes with
  `--test-threads=1` for stable numbers.

## Verdict: no runaway leak in the render hot path

The render path is memory-bounded by design and the probes confirm it:

- Render-cache LRU budget (64MB) + per-frame pruning
  (`bench_render_memory_growth_is_bounded`, 3000 frames ≈ 20+ min session):
  the cache oscillates in a sawtooth — grows to ~60MB, is pruned back to
  ~45MB — and the final assertion holds (real cache ≤ budget + slack). Heap
  in use grows only with the transcript content itself (the messages are
  inherently retained), NOT per frame.
- heaptrack profile of that same 3000-frame run
  (`/tmp/ht-longsession-profile.zst`):
  - peak heap 126.25M (native `mallinfo2` peaks at ~80MB: ~55MB transcript +
    ~46-61MB render cache), peak RSS incl. heaptrack 147.52M;
  - **total memory never freed at exit: 83.87K** — no accumulating leak;
  - 1,017,068 temporary allocations (all freed); the two busiest sites
    (`RawVec::finish_grow`, markdown `render_text`) are 91-100% temporary;
  - top consumers: `SessionView::render` 88.30M over 10,454 calls (the
    bounded render cache + markdown working set) and the test harness
    72.96M + 13.44M building the transcript (inherently growing data).
- Frame-time scaling is healthy: 50→3200 message pairs (64x) raises the warm
  frame median only 1.84x (37µs → 68µs); streaming frames stay ~constant
  (601→3001 messages = 5x, frame cost 1.00x). The O(n) per-frame message walk
  planned as a binary search in PERF-2026-07-19 is now a binary search over
  `prefix_y` (implemented 2026-08-12) — frame cost is O(log n + visible).
- `unique_agents()` (called every frame, O(n·k) scan + per-name clone): 15µs
  at 16k messages — acceptable, though it is pure per-frame work even when
  nothing changed.

## Found bottleneck #1: display_info() re-tokenizes everything (~33ms/call) — FIXED

**Location:** `src/harness/context_manager/mod.rs` — `display_info()` →
`total_tokens()` → `ContextItem::tokens()` → `TokenEncoding::estimate()` (full
tiktoken `encode_ordinary` per item).

**Measured (before):** 32,935µs (~33ms) per call with 1333 items / ~80k tokens.
The harness calls `display_info()` roughly 4x per agent-loop iteration — ~130ms
of pure snapshot work per iteration on a large session, growing linearly with
the transcript.

**Fix (applied):** `total_tokens()` now returns an incremental cached sum
(`cached_items_tokens`) kept in sync by every `items` mutation (all 4 add_*,
close_loop, remove_abandoned_inputs, pipeline_pass, trim_stale_tool_results,
remove_item, apply_llm_summary, restore_state, set_model with encoding-change
guard). `display_info()` is now O(1).

**Measured (after):** 0.00µs/call at 1333 items (~10,000x faster). Bonus: the
compaction funnel (`run()`) calls `total_tokens()` repeatedly and dropped from
288ms → ~78ms over a 2000-item overflow; the long-session test suite dropped
from 32s → 0.9s.

**Safety nets:** a debug-only brute-force cross-check in `total_tokens()`
fails fast on cache drift (costs nothing in release), plus
`cached_token_total_stays_in_sync_across_all_mutations` exercises every
mutation path in release. `long_session_display_info_cost_baseline` now
asserts the O(1) path (< 1ms fence, pre-fix ~33ms).

## Found bottleneck #2: one compaction run() = ~288ms over 2000 items — FIXED

**Location:** `src/harness/context_manager/mod.rs` — the funnel
(`pipeline_pass` / `evict_drafts` / `trim_stale_tool_results`) re-sums
`total_tokens()` (a full O(n) tiktoken pass) after every single step.

**Measured:** one `run()` over a 2000-item overflow took 287.6ms
(`long_session_run_cost_is_measured`). The cost is O(N) per step × O(N) steps
= O(N²) re-tokenization in the worst case.

**Why it matters:** `run()` is awaited after every dispatch phase; a single
overflow on a large session blocks the agent loop for ~0.3s of pure local
compute (plus the deterministic compression itself).

**Fix (applied, on top of the #1 cache):** a **per-item token cache**
(`item_tokens: HashMap<u64, usize>`) so every in-place edit and removal reads
the OLD cost from the map instead of re-tokenizing the content through
tiktoken:

- `trim_stale_tool_results` was the dominant term (profiled: 49ms of 63.7ms):
  it re-ran `estimate(full content)` per result — ~1ms per ~2k-token result,
  so the pass cost scaled with the TOTAL size of held tool results (the
  classic long-session stall). Now only the small preview is tokenized.
- `pipeline_pass` reads the draft's old (possibly compressed) cost from the
  map; `remove_item` (all 3 branches), `close_loop` and
  `remove_abandoned_inputs` too.
- `sweep_useless_chains` was O(n²) — `chain_is_useless` scanned the timeline
  per tool item; now a single precomputed `HashSet<String>` of useless call
  ids makes the sweep O(n).

**Measured (after, release):**

| Phase | Before | After |
|---|---|---|
| `run()` over 2000 items | 288ms | **~40ms** |
| `run()` w/ 300 large (~2k-token) results | ~350ms | **~15ms** |
| `trim_stale_tool_results` (300 large results) | ~300ms | **~10ms** |
| `sweep_useless_chains` (1200 items) | ~2ms (O(n²)) | **~0.5ms** (O(n)) |

**Safety nets:** the debug-only cross-check now ALSO validates the per-item
map against the items themselves (`len` + per-id equality) — it caught a real
pre-existing bug: a test pushing `Compaction { id: 1 }` by hand collided with
the internal counter's next id, duplicating an id (invisible before the map).
`push_raw` now advances the counter past manual ids. New regression fences:
`long_session_run_cost_is_measured` (<1s vs ~40ms), new
`long_session_trim_large_results_stays_cheap` (<250ms vs ~10ms) and
`long_session_useless_sweep_stays_linear` (<100ms vs ~0.5ms).

## Found accumulation #3: ToolRenderState expansion maps never evict

**Location:** `src/tui/routes/session/tool_render.rs` —
`expanded` / `error_expanded: HashMap<String, bool>`.

**Measured:** 5000 toggle interactions leave 7500 permanent entries (~187KB by
entry size alone, no eviction). The spinner map is swept every frame
(`sweep_idle_spinners`), but the expansion maps are insert-only — every
distinct tool call id the user expands stays forever.

**Why it matters:** small per entry, but unbounded over a long session with
many expand/collapse interactions. Documented by
`bench_tool_state_expansion_maps_stay_small`.

## Bounded-by-design (verified, no action needed)

- ContextManager long tool loop: 600 rounds peak at 81,968 tokens / 1800
  items — the retention trim (`trim_stale_tool_results`) and draft eviction
  keep the total far below the 1.5M raw tokens the session would hold without
  them (`long_session_tool_loop_keeps_tokens_bounded`).
- Render cache + scratch buffer + idle-spinner sweep (above).
- `NeedsLlmCompaction` after ~585 tool rounds with a 100k budget is the
  designed last-resort fallback (protected items accumulate), not a leak.

## How to run the probes

```bash
# TUI render probes (release, single-threaded for stable timings)
cargo test --release --bin tui bench_ -- --ignored --test-threads=1 --nocapture

# Harness context probes (release only — tiktoken is 10-20x slower in debug)
cargo test --release -p cosh --lib harness::context_manager::test::long_session -- --ignored --nocapture

# heaptrack profile (minimal 6-frame render)
cargo test --release --bin tui bench_render_heaptrack_minimal -- --ignored
heaptrack ./target/release/deps/tui-<hash> bench_render_heaptrack_minimal --ignored
heaptrack_print <profile>.zst

# heaptrack profile of the FULL 3000-frame long session (~20+ min session
# equivalent). NOTE: heaptrack's per-allocation interception makes this slow
# (the run finishes, but let it run detached — the profile is written at
# exit; expect several minutes and run it in the background):
#   heaptrack ./target/release/deps/tui-<hash> \
#       bench_render_memory_growth_is_bounded --ignored --nocapture
#   heaptrack_print heaptrack.*.zst | grep -E 'peak heap|total memory leaked|temporary memory'
```
