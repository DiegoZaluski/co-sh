# BUG-2026-07-06: Silent Deadlock in `build_extractor()` via `std::sync::Mutex` + `vec!` Temporary Lifetime Interaction

## Symptoms

When a user sends a message to the agent loop (`Harness::run_agent_loop()`):

1. The HTTP request to the LLM provider succeeds (200 OK).
2. The streaming response is received (`stream_chat_with_system` returns `Ok`).
3. The code then hangs **forever** — no tokens appear in the TUI, no errors are shown, the agent spinner spins indefinitely.
4. The TUI is still responsive (you can navigate, open menus), but the agent loop never completes.
5. The OS thread running the agent loop is stuck in a **blocking** state — 100% stuck, not polling or waiting for I/O.

The hang is **silent**: no panic, no error message, nothing logged. The `catch_unwind` wrapper doesn't fire because there's no panic — it's a genuine deadlock at the OS thread level.

## The Root Cause: A Deadlock on `std::sync::Mutex`

The hang is a **deadlock** caused by trying to `lock()` a `std::sync::Mutex` from the same thread that already holds the lock. `std::sync::Mutex` in Rust is **non-reentrant**: if thread A holds the lock and thread A tries to `lock()` again (without unlocking first), the thread blocks **forever**. On Linux, this is implemented with `pthread_mutex_lock` using a non-recursive mutex type — the second `lock()` simply never returns.

This is NOT a panic, NOT an error, NOT a timeout. It's an OS-level thread block. The thread scheduler sees the thread as "waiting for a futex" and parks it permanently.

## The Trigger: The `vec!` Macro + Temporary Lifetime Rules

### The code

In `src/harness/tools.rs`, the `CoshTools::schemas()` method (part of the `Tools` trait implementation) builds a `Vec<ToolSchema>` by reading fields from various tool structs. The `plan` field uses a mutex:

```rust
// libstd's std::sync::Mutex, NOT tokio::sync::Mutex
pub struct CoshTools {
    bash: Bash,
    fs: Fs,
    find: Find,
    web: Web,
    vision: Vision,
    plan: Mutex<Plan>,       // <--- std::sync::Mutex
    question: Question,
    skills: Skills,
}
```

The `schemas()` method was written as a single `vec!` macro call:

```rust
fn schemas(&self) -> Vec<ToolSchema> {
    vec![
        // ... 10 non-Mutex fields ...
        extract_schema(&self.plan.lock().unwrap().description_todo_write),
        extract_schema(&self.plan.lock().unwrap().description_todo_edit),
        extract_schema(&self.plan.lock().unwrap().description_todo_cross_off),
        extract_schema(&self.plan.lock().unwrap().description_todo_read),
        extract_schema(&self.plan.lock().unwrap().description_load_from_md),
        // ... 5 more non-Mutex fields ...
    ]
}
```

### How `vec!` actually works

The `vec!` macro expands to something like:

```rust
{
    let mut v = Vec::new();
    v.push(extract_schema(&self.plan.lock().unwrap().description_todo_write));
    v.push(extract_schema(&self.plan.lock().unwrap().description_todo_edit));
    v.push(extract_schema(&self.plan.lock().unwrap().description_todo_cross_off));
    v.push(extract_schema(&self.plan.lock().unwrap().description_todo_read));
    v.push(extract_schema(&self.plan.lock().unwrap().description_load_from_md));
    v
}
```

Each `v.push(...)` evaluates its argument expression. The argument `extract_schema(&self.plan.lock().unwrap().description_todo_write)` does:

1. `self.plan.lock()` — calls `Mutex::lock()`, which returns `LockResult<MutexGuard<Plan>>`.
2. `.unwrap()` — unwraps the `Result`, giving a `MutexGuard<Plan>`.
3. `.description_todo_write` — accesses the `description_todo_write` field through the guard's `Deref` impl.
4. `extract_schema(&...)` — takes a reference to the field and reads it.

The `MutexGuard` is a **temporary value** (it is not bound to a named variable).

### Rust's Temporary Lifetime Rule

Here is the critical language rule. In Rust, **temporaries** (values not bound to a `let` binding) live until the end of the **enclosing statement**.

- In `let x = foo(bar());`, the temporary from `bar()` lives until the `;` of the `let` statement. When `foo()` returns, the temporary is dropped.
- In `let v = vec![a(), b()];`, the temporaries from `a()` and `b()` live until the `;` of the `let` statement. **Both temporaries are alive simultaneously** for the duration of the entire `vec!` expression.

This means the `MutexGuard` from `self.plan.lock()` in the FIRST vec element (`description_todo_write`) is **still alive** when the SECOND element (`description_todo_edit`) is evaluated.

And when the second element calls `self.plan.lock()`, it finds the mutex is **already locked by the current thread**. Since `std::sync::Mutex` is non-reentrant, `lock()` blocks forever.

### The Deadlock, Step by Step

1. Thread enters `schemas()`.
2. `vec!` macro starts evaluating elements left-to-right.
3. **Element 1**: `self.plan.lock()` → **lock acquired**. Returns `MutexGuard<Plan>` (temporary #1).
4. `.description_todo_write` is read, `extract_schema()` clones it. Result pushed to `v`.
5. Temporary #1 is **NOT dropped yet** — it lives until the `;` of the `let v = vec![...]` statement.
6. **Element 2**: `self.plan.lock()` → tries to acquire the lock, but **temporary #1 still holds it**.
7. `pthread_mutex_lock` sees the mutex is locked by the current thread. For a non-recursive mutex, this is a **deadlock** — the thread blocks forever.
8. The thread never reaches element 3, 4, or 5. It never returns from `schemas()`. It never returns from `build_extractor()`. It never returns from `stream_chat()`. It never returns from `run_agent_loop()`.
9. The `catch_unwind` wrapper does nothing because there's no panic — just a blocked OS thread.
10. The TUI's spinner keeps spinning because it never receives a `Done` or `Error` event.

The deadlock is permanent. The thread will never wake up. The TUI will hang forever (or until the user kills the process with Ctrl+C).

### Why `write_tool_descriptions()` did NOT have this bug

```rust
fn write_tool_descriptions(&self, out: &mut String) {
    // ...
    {
        let plan = self.plan.lock().unwrap();   // ONE lock, bound to a let
        write_single_tool(out, &plan.description_todo_write);
        write_single_tool(out, &plan.description_todo_edit);
        write_single_tool(out, &plan.description_todo_cross_off);
        write_single_tool(out, &plan.description_todo_read);
        write_single_tool(out, &plan.description_load_from_md);
    }   // plan guard dropped HERE
    // ...
}
```

This acquires the lock **once** and holds it for all 5 reads. The guard is bound to a named `let` variable and dropped at the closing `}`. Only **one** `lock()` call, so no deadlock.

### Why the bug only manifested with `run_agent_loop`

The old working code (commit `2b904a2`) used **direct streaming**:

```rust
// OLD CODE — worked
connector.stream_chat_with_system(&input, &header_context).await {
    Ok(mut stream) => {
        while let Some(chunk) = stream.next().await {
            // stream tokens directly to TUI
            event_tx.send(Token { text: token });
        }
        event_tx.send(Done);
    }
}
```

This code **never called `schemas()`**. It never built an extractor. It never called `build_extractor()`. So the deadlock never triggered.

The new code uses `Harness::run_agent_loop()`:

```rust
// NEW CODE — deadlock
let mut harness = Harness::new(connector, ".");
harness.format_header_context();        // calls write_tool_descriptions() — one lock, fine
harness.run_agent_loop(&input, ...).await;
    // → stream_chat()
    //   → build_extractor()
    //     → cosh.schemas()
    //       → vec![ ... plan.lock()... plan.lock()... ]  ← DEADLOCK
```

The execution path is:
`app.rs::SendMessage` → `tokio_handle.spawn()` → [`std::thread::spawn` after Fallback Plan] → `rt.block_on(async { ... })` → `Harness::run_agent_loop()` → `stream_chat()` → `build_extractor()` → `cosh.schemas()` → `vec![...plan.lock()...plan.lock()...]` → **DEADLOCK on second `lock()`**.

### Why `finish_reason` didn't matter, why `format_header_context` didn't matter, why runtime selection didn't matter

All the previous hypotheses from NOBUG.md were **distractions**:

| Hypothesis | Why it didn't matter |
|---|---|
| `finish_reason` not checked | The stream never got to yield any chunks — it deadlocked BEFORE the first `stream.next().await` |
| `format_header_context()` not called | Even when called, it used `write_tool_descriptions()` (single lock) — fine |
| Runtime: `multi_thread` vs `current_thread` | `std::sync::Mutex` deadlocks on ANY runtime — it's an OS-level thread block |
| Silent panic | Not a panic — it's a deadlock, unrecoverable without OS intervention |
| `reqwest::Client::new()` context | The HTTP request succeeded (200 OK) — the client was fine |
| Event channel issues | The channel was never used — the code deadlocked before sending any events |
| `answer_rx.recv()` blocking | Never reached the answer channel — deadlocked in Phase 1's `stream_chat()` |

## The Fix

**Split the `vec!` macro into individual `v.push()` statements**, each ending with `;`:

```rust
fn schemas(&self) -> Vec<ToolSchema> {
    let mut v = vec![
        // non-Mutex fields — safe to batch in one vec!
        extract_schema(&self.bash.description_run),
        extract_schema(&self.fs.description_read),
        // ... etc ...
    ];
    // Mutex fields — each push is its OWN statement
    v.push(extract_schema(&self.plan.lock().unwrap().description_todo_write));
    // guard dropped HERE — at the ;
    v.push(extract_schema(&self.plan.lock().unwrap().description_todo_edit));
    // guard dropped HERE — at the ;
    v.push(extract_schema(&self.plan.lock().unwrap().description_todo_cross_off));
    // guard dropped HERE — at the ;
    v.push(extract_schema(&self.plan.lock().unwrap().description_todo_read));
    // guard dropped HERE — at the ;
    v.push(extract_schema(&self.plan.lock().unwrap().description_load_from_md));
    // guard dropped HERE — at the ;
    v.push(extract_schema(&self.question.description_ask));
    v.push(extract_schema(&self.skills.description_list));
    // ... etc ...
    v
}
```

Each `v.push(...)` is a **full statement** (terminated by `;`). The temporary `MutexGuard` created by `self.plan.lock().unwrap()` lives until the `;`, and is **dropped before the next `v.push()` begins**. Each `lock()` call finds the mutex unlocked, acquires it, and releases it before the next call.

## The Broader Lesson: `std::sync::Mutex` + `vec!` = Danger

Any time you have `vec![ expr_with_lock(), expr_with_lock(), ... ]`, you risk this deadlock. The fix is:

1. **Use `v.push()` statements** instead of the `vec!` macro for Mutex-accessed fields.
2. **Or acquire the lock once** and store the guard in a `let` binding (like `write_tool_descriptions` does).
3. **Or use `tokio::sync::Mutex`** instead of `std::sync::Mutex` — `tokio::sync::Mutex` is reentrant-safe because it's designed for async use, and its `.lock()` method returns a future that can handle this correctly. However, `tokio::sync::Mutex` has overhead and should not be used for simple field accesses in synchronous code.

### Why `tool_descriptions()` has the SAME bug

The same file (`tools.rs`) has another method with the same pattern:

```rust
fn tool_descriptions(&self) -> Vec<serde_json::Value> {
    vec![
        self.bash.description_run.clone(),
        // ... 10 non-Mutex fields ...
        self.plan.lock().unwrap().description_todo_write.clone(),
        self.plan.lock().unwrap().description_todo_edit.clone(),
        // ... same deadlock here! ...
    ]
}
```

This method is also vulnerable to the same deadlock, but it was never called in the current execution path (only `schemas()` was called via `build_extractor()`).

## Summary

```
Thread enters schemas()
  → vec! evaluates element 1
    → plan.lock()          OK — lock acquired
    → ...read field...
    → MutexGuard NOT dropped (temporary lives until ;)
  → vec! evaluates element 2
    → plan.lock()          DEADLOCK — same thread, same mutex, non-reentrant
    → thread blocks forever on pthread_mutex_lock
  → vec! never completes
→ schemas() never returns
→ build_extractor() never returns
→ stream_chat() never returns
→ run_agent_loop() never returns
→ TUI spinner spins forever, no Done, no Error
```

The fix was to replace `vec![...plan.lock()...plan.lock()...]` with separate `v.push(...plan.lock()...);` statements, ensuring each `MutexGuard` is dropped before the next `lock()` call.
